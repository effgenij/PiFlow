## 1. Linear MCP + OpenSpec: A Spec-Driven Development Workflow
**Дата:** January 11, 2026  
**Ссылка:** [/blog/2026/01/11/linear-mcp-openspec-sdd-workflow/](https://intent-driven.dev/blog/2026/01/11/linear-mcp-openspec-sdd-workflow/)

### Суть
Статья отвечает на три главных вопроса, которые возникают при попытке внедрить Spec-Driven Development (SDD) в существующую команду:

1. **Стартовая точка** — можно использовать существующий бэклог (Jira, Azure DevOps, GitHub Issues, Linear) как источник задач для SDD, не нужно начинать с нуля.
2. **Роли и доступ** — команда продукта не обязана иметь доступ к Git для просмотра спецификаций; интеграция с Linear решает это через веб-интерфейс.
3. **Монорепо vs отдельный репозиторий** — спеки можно хранить отдельно от кода, хотя колокация имеет преимущества.

### Ключевая идея
Плавный онбординг важнее идеального процесса. Показать ценность SDD на знакомом инструменте (Linear) — эффективнее, чем сразу требовать смены всего рабочего процесса.

## 2. OpenSpec 1.0 Release
**Дата:** January 26, 2026  
**Ссылка:** [/blog/2026/01/26/openspec-1-0-release/](https://intent-driven.dev/blog/2026/01/26/openspec-1-0-release/)

### Суть
OpenSpec 1.0 — первый стабильный релиз инструмента для Spec-Driven Development. Основная концепция: **спецификации как единственный источник истины**, к которому привязывается весь процесс разработки.

### Ключевые изменения в 1.0
- **CLI-команды**: `init`, `propose`, `apply`, `archive` — чёткий жизненный цикл изменения.
- **Мультиагентная поддержка** — несколько агентов могут работать параллельно.
- **Система конфигурации** — позволяет подключать внешние инструменты (например, Linear через MCP) без форка OpenSpec.
- Спецификации хранятся рядом с кодом и читаются агентами как контекст при каждом изменении.

## 3. The Intent Harness
**Дата:** February 23, 2026  
**Ссылка:** [/blog/2026/02/23/intent-harness/](https://intent-driven.dev/blog/2026/02/23/intent-harness/)

### Суть
Описывает двухуровневую архитектуру между человеком и агентом:

- **Agentic Harness** (нижний уровень) — слой исполнения: инструменты, управление потоком, память, гарантии безопасности. Направляет возможности LLM в полезную работу.
- **Intent Harness** (верхний уровень) — слой артикуляции: помогает человеку превратить размытую идею в структурированное, явное намерение, которое агент может выполнить без постоянного надзора.

### Проблема, которую решает
Идеи рождаются как интуиция — неполная и неструктурированная. Если отправить эту неопределённость напрямую в систему исполнения, результат: поверхностные промпты, слабые задачи, вывод, требующий постоянного контроля человека.

### Механизм
Intent Harness создаёт диалог между человеком и AI для выработки общего понимания. **Spec-Driven Development** — главный инструмент этого слоя: спецификации фиксируют intent, ограничения и критерии успеха в явном виде до начала реализации.

## 4. OpenSpec 1.2 Release
**Дата:** February 25, 2026  
**Ссылка:** [/blog/2026/02/25/openspec-1-2-release/](https://intent-driven.dev/blog/2026/02/25/openspec-1-2-release/)

### Суть
OpenSpec 1.2 вводит **профили** — пресеты рабочего процесса:

| Профиль | Поток | Для кого |
|---------|-------|----------|
| **Core** | `explore → propose → apply → archive` | Большинство проектов, стандартный подход |
| **Custom** | Шаговое прохождение артефактов (`continue`) или генерация всего сразу (`fast-forward`) | Расширенные сценарии, кастомные схемы |

### Ключевые отличия от 1.0/1.1
- `explore` — новая фаза перед `propose`: агент изучает проект перед тем как предлагать изменения.
- `propose` в Core генерирует все артефакты (proposal.md, spec.md, design.md, tasks.md) за один раз.
- Custom Profile даёт доступ к расширенным командам для пошагового управления.

## 5. Spec-Driven Development with Brownfield Projects
**Дата:** March 10, 2026  
**Ссылка:** [/blog/2026/03/10/spec-driven-development-brownfield/](https://intent-driven.dev/blog/2026/03/10/spec-driven-development-brownfield/)

### Суть
Применение SDD к legacy-проектам (brownfield) — задача нетривиальная. Статья объясняет почему наивный подход не работает и предлагает практическую альтернативу.

### Почему нельзя просто «отреверс-инженерить» спеки
1. **Дорого и неэффективно** — полное восстановление спецификаций по коду требует огромных усилий.
2. **Проблема рассмотрения** — даже получив спеки, их нереально проревьювить целиком.
3. **Alignment loss** — обратно выведенная спека является производным артефактом. Когда новые фичи разрабатываются против неточной спеки, резко возрастает риск регрессий.

### Аналогия с TDD
Как в «Working Effectively with Legacy Code» (Feathers) не пишут все тесты сразу, а покрывают тестами только область изменяемого кода — так и спеки в brownfield пишутся **инкрементально**.

### Рекомендуемый подход: Change-Driven Specs
- Спека пишется только для области, которую вы сейчас меняете.
- Каждое изменение в кодовой базе сопровождается соответствующей спекой.
- Постепенно спеки накапливаются и покрывают систему органически.

## 6. OpenSpec, Git WorkTrees and OpenCode
**Дата:** April 1, 2026  
**Ссылка:** [/blog/2026/04/01/openspec-git-worktrees-opencode/](https://intent-driven.dev/blog/2026/04/01/openspec-git-worktrees-opencode/)

### Суть
Git WorkTrees позволяют одновременно держать несколько веток в отдельных директориях — каждая с собственным рабочим состоянием. В связке с SubAgents в OpenCode это обеспечивает **параллельную разработку фич** в рамках SDD-воркфлоу.

### Где выполняется каждый шаг OpenSpec

| Шаг OpenSpec | Где выполняется |
|---|---|
| `propose` | `main` — предложение изменения |
| `apply` | Отдельный worktree на feature-ветке |
| `archive` | После merge обратно в `main` |

### Преимущества
- Агенты не мешают друг другу — каждый работает в своём worktree.
- Proposal согласуется на `main`, реализация происходит изолированно.
- Merge возвращает результат в `main`, после чего изменение архивируется.

## 7. Architectural Decision Records with Spec-Driven Development using OpenSpec
**Дата:** April 29, 2026  
**Ссылка:** [/blog/2026/04/29/spec-driven-development-with-adr/](https://intent-driven.dev/blog/2026/04/29/spec-driven-development-with-adr/)

### Суть
Кастомная схема `spec-driven-with-adr` добавляет к стандартному OpenSpec-воркфлоу артефакт **Architectural Decision Record (ADR)** как полноценный участник процесса, а не документ в стороне.

### Чем отличается от стандартной схемы
- ADR-артефакт **живёт вне папки изменения** (`openspec/`) и **сохраняется после архивирования**.
- Каждое изменение может создавать один или несколько ADR (при значимых архитектурных решениях).
- ADR фиксируют: контекст, рассмотренные варианты, принятое решение и его последствия — в момент принятия решения.

### Зачем это нужно
- Дурабельная история архитектурных решений доступна будущим контрибьюторам (людям и агентам) без необходимости копаться в PR, Slack или памяти.
- Текущее состояние архитектуры видно в явном виде и служит контекстом для следующих изменений.

## 8. Spec-Driven Development with OpenSpec and OpenCode
**Дата:** May 10, 2026  
**Ссылка:** [/blog/2026/05/10/spec-driven-development-openspec-opencode/](https://intent-driven.dev/blog/2026/05/10/spec-driven-development-openspec-opencode/)

### Суть
Сквозной разбор [`intent-driven-template`](https://github.com/intent-driven-dev/intent-driven-template) — готового шаблона, который объединяет OpenSpec, OpenCode и набор кастомных скиллов в единый SDD-воркфлоу.

### Шаги воркфлоу, которые настраивает шаблон

1. **`openspec init`** — инициализация проекта с кастомной схемой.
2. **Explore** — агент изучает проект (автоматически запускается brainstorming-скилл из Superpowers).
3. **Propose** — создание артефактов: `proposal.md`, `spec.md`, `design.md`, `tasks.md`.
4. **Apply** — реализация задач из `tasks.md`.
5. **Archive** — завершение изменения.

### Параллелизм через Worktrees
- Скилл `openspec-bulk-apply-change` запускает несколько изменений параллельно — каждое в своём worktree и SubAgent.
- Агенты не конкурируют за файлы: proposal на `main`, реализация в worktree, merge перед archive.

### Кастомная схема
Шаблон использует собственный YAML-файл схемы, который определяет артефакты, их шаблоны, инструкции для агента и зависимости между артефактами. Это позволяет адаптировать воркфлоу под проект без изменения самого OpenSpec.

## Сквозные концепции (без повторений)

| Концепция | Описание |
|---|---|
| **Spec as Source of Truth** | Спецификации — первичный артефакт, код — производный. Всё привязывается к спекам. |
| **Change-Driven Workflow** | Единица работы — «изменение» (change): proposal → spec → design → tasks → apply → archive. |
| **Incremental Adoption** | SDD внедряется постепенно: brownfield — через change-driven specs, команды — через знакомые инструменты (Linear). |
| **Parallel Execution** | Git WorkTrees + SubAgents позволяют нескольким агентам работать изолированно и параллельно. |
| **Durable Artifacts** | ADR, спеки, решения хранятся рядом с кодом и читаются агентами как контекст в будущем. |
| **Intent Harness** | Двухуровневая система: Intent Harness (артикуляция идеи) + Agentic Harness (исполнение). |
